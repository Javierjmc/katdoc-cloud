1Objetivo y cómo usar este manual

Este manual es una guía operativa para revisar la app en producción: cada módulo de la interfaz, los servicios de backend, la base de datos y el cron automático. No es documentación de desarrollo: es una lista de comprobación para validar el estado VIVO del sistema.

Modo de uso

  • Ejecutar en un navegador real (desktop y móvil) contra la URL de producción.
  • Marcar ☐ cada ítem conforme pasa. Si algo falla, anotar en la columna de comentarios / hoja de hallazgos (sección 10).
  • Los ítems marcados con CRÍTICO deben funcionar sí o sí; si fallan, la app no se considera operativa.
  • Antes de empezar, tener a mano: URL de producción, PIN de acceso, acceso al dashboard de Supabase y al proyecto de Vercel.
Entorno de referencia. Proyecto Supabase: sjuditnsedkahilgcovi · Cron Vercel: /api/reminders/scan a las 13:00 UTC. Estos datos se confirman en la sección 8.

2Acceso y seguridad

2.1 Login

  • Al abrir / se redirige a /login (no al dashboard) sin sesión. middleware.ts
  • El teclado numérico de PIN acepta exactamente 4 dígitos y valida solo al completarlos. app/login/page.tsx
  • CRÍTICO Con PIN correcto entra al dashboard; con PIN incorrecto muestra "PIN incorrecto", hace shake y limpia el campo. validatePin()
  • Tras loguear, al recargar cualquier página interna se mantiene la sesión (no vuelve a pedir PIN). sessionStorage vetcare_auth
  • El botón Cerrar sesión en el menú vuelve a /login y revoca el acceso. AppShell.handleLogout()
  • Si la sesión expira o se limpia el storage, las rutas protegidas redirigen a /login (sin pantalla rota). auth check en cada página
Nota de seguridad. La autenticación es un PIN en sessionStorage (client-side). Es suficiente para el uso clínico interno, pero no es autenticación fuerte. No hay RLS en las tablas: la anon key tiene acceso de lectura/escritura completo. Si se van a manejar datos sensibles o multi-clínica, migrar a Supabase Auth + RLS (deuda técnica conocida, ver sección 11).

2.2 Protección de API routes

2.3 Pruebas rápidas de API

  • CRÍTICO GET /api/reminders/scan sin header devuelve 401.
  • GET /api/reminders/scan con header x-app-pin: <PIN> devuelve 200 con {"creados":N,"existentes":N,"errores":N}.
  • POST /api/exams/parse sin header devuelve 401; con archivo inválido devuelve 400.
  • POST /api/notifications/email sin header devuelve 401.
Importante: no abrir /api/reminders/scan en el navegador directo sin header de PIN, salvo que se quiera confirmar el 401.

3Dashboard

Ruta /dashboard · Estadísticas generales + próximos eventos + buscador global + listado de pacientes.

3.1 Estadísticas y carga

  • Se muestran 3 tarjetas: Tutores, Pacientes y Consultas con conteos reales de la BD. dashboard_search
  • La pantalla muestra skeletons mientras carga (sin flashes de contenido incorrecto).
  • El botón Nuevo Paciente lleva a /patients/new.

3.2 Próximos eventos (7 días)

  • Se listan citas programadas/confirmadas y próximas vacunas, desparasitaciones y controles de examen de los próximos 7 días. useCalendarEvents
  • El estado vacío muestra "Sin citas ni controles pendientes esta semana." sin errores.
  • Cada evento muestra tipo (badge de color), paciente, fecha y hora, y enlaza al perfil del paciente.
  • El link Ver agenda › abre /agenda.

3.3 Buscador y filtros

  • El buscador encuentra por mascota, tutor, cédula y n° de historia (con debounce de 250 ms).
  • El filtro de especie (chips) filtra el listado y se recuerda entre sesiones. localStorage
  • Con búsqueda sin resultados muestra "Sin resultados"; sin datos muestra estado vacío con CTA Registrar paciente.

3.4 Listado y paginación

  • Se muestran tarjetas de paciente (foto o emoji, nombre, especie, tutor, n° historia, fecha de última consulta).
  • Con más de 9 resultados aparece el botón Cargar más y funciona.
  • Cada tarjeta enlaza a /patients/<id>.

4Pacientes

Rutas /patients · /patients/new · /patients/[id] · /patients/[id]/edit · /patients/[id]/reporte.

4.1 Listado

  • Pestañas Activos / Inactivos con conteos correctos.
  • Vista Grid y Lista funcionan y se recuerdan entre sesiones. localStorage patients_view
  • Buscador por nombre, raza, tutor y cédula + filtro de especie.
  • Paginación Cargar más (12 por página) funciona.
  • Los pacientes inactivos se marcan visualmente (Inactivo).

4.2 Crear paciente (formulario)

  • CRÍTICO Se puede registrar un paciente nuevo con tutor (nuevo o existente), especie, datos y foto. PatientForm
  • La validación zod rechaza datos incompletos mostrando errores por campo. lib/schemas.ts
  • La foto se sube al bucket pet-photos y se muestra tras guardar.
  • El botón Editar en el perfil permite modificar datos y foto.
  • Se puede desactivar un paciente (pasa a pestaña Inactivos y deja de generar recordatorios).

4.3 Perfil del paciente

  • El perfil muestra: datos de la mascota, tutor, foto, edad calculada.
  • Secciones de historial: consultas, vacunas, exámenes, recetas, ecografías, citas.
  • Botón para crear nueva consulta (va a /records/new?patientId=).
  • Botón para generar reporte/impresión (imprimir historial por navegador).
  • El historial clínico de un paciente con varias consultas se lista ordenado (más reciente primero).
Dato. El n° de historia clínica es correlativo generado en BD por generate_numero_historia().

5Tutores / Propietarios

Rutas /tutors · /tutors/[id] · /tutors/[id]/edit.

  • El listado muestra todos los propietarios con su cédula, teléfono y n° de mascotas.
  • El buscador filtra por nombre, cédula, teléfono o nombre de mascota.
  • Expandir un tutor muestra email, dirección, botón Editar tutor y sus mascotas.
  • CRÍTICO Agregar mascota desde un tutor pre-rellena el formulario de nuevo paciente con sus datos. buildNewPetUrl()
  • Cada mascota enlaza a su perfil.
  • Editar tutor permite corregir datos de contacto y persiste.
  • Paginación Cargar más (10 por página) funciona.
Verificar: si un tutor tiene 0 mascotas, muestra el mensaje "Sin mascotas — Registrar primera" con enlace funcional.

6Agenda y citas

Ruta /agenda · Calendario mensual con citas + próximas vacunas/desparasitaciones/controles de examen + agendado de citas.

6.1 Calendario

  • El calendario mensual se muestra correcto (días alineados, leyenda de tipos arriba en desktop).
  • La navegación ‹ › cambia de mes y el botón Hoy vuelve al mes/fecha actual.
  • Los eventos del día aparecen con su color: Cita (brand), Vacuna (azul), Desparasitación (verde), Control examen (amarillo).
  • Si un día tiene más de 3 eventos muestra "+N más".
  • Hacer click en un día abre el panel de detalle del día.

6.2 Agendar cita

  • CRÍTICO El botón + Agendar cita abre el modal con paciente (requerido), hora, motivo y notas.
  • La validación zod exige seleccionar paciente; campos malos marcan error y muestran toast. appointmentSchema
  • Al guardar, la cita aparece en el día correspondiente con estado Programada.
  • La cita generada crea su recordatorio al correr el scan (sección 8).
  • En el perfil del paciente el módulo de citas permite cambiar estado (programada/confirmada/completada/cancelada/no asistió).
Verificar: las citas con estado programada o confirmada aparecen también en "Próximos eventos" del dashboard.

7Historias clínicas

Rutas /records/new · /records/[id] · Formulario médico completo.

7.1 Nueva consulta

  • CRÍTICO Se puede crear una historia clínica para un paciente activo con su n° de historia correlativo auto-asignado. getNextNumeroHistoria()
  • El formulario incluye: anamnesis, motivo, constantes vitales, checklist de los 12 sistemas clínicos (N / AN / NE), notas por sistema, hallazgos y adjunto PDF. SISTEMAS_CONFIG
  • Los sistemas con estado Anormal se resaltan y permiten nota de descargo.
  • Se puede adjuntar un documento (bucket medical-documents) y se enlaza desde la historia.
  • Guardar persiste y redirige a /records/[id].

7.2 Detalle de historia

  • La vista muestra todos los datos de la consulta y los estados de sistemas.
  • Permite editar la historia.
  • Permite imprimir / guardar como PDF (impresión por navegador).
Limitación conocida: el "PDF" es impresión por navegador (Ctrl+P), no un archivo generado server-side. Verificar que la vista de impresión salga legible.

7.3 Exámenes de laboratorio (IA)

  • CRÍTICO Se puede subir un examen (PDF/imagen) y el sistema extrae analitos con Gemini: nombre del examen, laboratorio, fecha, tabla de analitos con flag N/ALTO/BAJO. /api/exams/parse
  • Se permite editar/corregir los analitos extraídos y guardar.
  • Si la IA no encuentra datos devuelve error claro: "No se pudo extraer información…".
  • Si GEMINI_API_KEY no está configurada, la subida responde 503 con mensaje (verificar en producción que responde 200).

7.4 Vacunas y desparasitaciones

  • Se registra vacuna con nombre, fecha de aplicación y fecha de próxima dosis (opcional).
  • Las desparasitaciones se detectan por palabra clave del nombre (drontal, milbemax, etc.). guessTipo()
  • Una vacuna con próxima dosis genera su recordatorio en la ventana configurada.

7.5 Recetas y ecografías

  • Las recetas permiten agregar medicamentos (nombre, presentación, dosis, frecuencia, duración, vía, indicaciones) y editar antes de guardar/imprimir.
  • Las ecografías permiten registrar órgano, hallazgos, conclusiones, mediciones e imágenes (bucket ecografias).

8Notificaciones y recordatorios

Rutas /notifications · /config · Motor automático /api/reminders/scan.

8.1 Centro de notificaciones

  • Pestaña Pendientes agrupa recordatorios Vencidos (rojo) y Próximos (naranja) con paciente, tutor, fecha y tipo.
  • CRÍTICO El botón 🔍 Chequear ahora corre el scan y muestra toast con cuántos recordatorios nuevos creó. runScanNow()
  • Acciones por recordatorio: WhatsApp (abre wa.me), Email, ✓ Enviado, ⏰ Sin respuesta, Descartar.
  • Pestaña Seguimiento lista clientes sin respuesta con días transcurridos y historial de intentos (log).
  • En seguimiento se puede re-enviar WhatsApp/email, marcar Respondió, volver a pendiente o descartar.

8.2 Motor de recordatorios (scan) — verificación

  • CRÍTICO El scan crea recordatorios para: vacunas/desparasitaciones con próxima dosis, exámenes con próximo control y citas programadas/confirmadas, solo de pacientes activos. lib/notifications/scan.ts
  • Es idempotente: correrlo dos veces no duplica recordatorios (UNIQUE patient+tipo+fecha+título).
  • Solo crea el recordatorio si la fecha está dentro de la ventana: días_antes del evento hasta máx(días_despues, 3) días después.
  • CRÍTICO El cron de Vercel dispara /api/reminders/scan todos los días a las 13:00 UTC. vercel.json
  • Para probar: correr el scan manual desde el botón y verificar que el conteo crece correctamente.

8.3 Configuración de ventanas (/config)

  • Existen 6 tipos por defecto: vacuna, desparasitacion, examen, control, cita, seguimiento, cada uno con días antes/después y toggle enabled. notification_config
  • Los presets rápidos (7, 21, 30, 45, 60, 90 días) actualizan el valor al click.
  • Se pueden editar días antes/después por input y activar/desactivar.
  • Se puede agregar un tipo personalizado y eliminar uno existente (con confirmación).
  • Los cambios persisten y afectan el siguiente scan.

8.4 Canales de envío

  • WhatsApp: abre wa.me con el mensaje pre-armado (envío manual por el staff).
  • Email: si RESEND_API_KEY está configurada, envía vía Resend; si no, abre mailto: y avisa "Resend no configurado". provider.ts
  • Todo envío registra en notification_log (historial de intentos).
Check específico de prod: confirmar si el email usa onboarding@resend.dev (solo envía al dueño) o un dominio verificado. Para envíos reales a clientes debe haber un dominio verificado en Resend.

9Infraestructura y plataforma

9.1 Vercel

  • El deploy de producción corresponde a la rama main (o la configurada) y está último commit.
  • Los deploys de producción terminan en estado Ready sin errores de build.
  • Las 7 variables de entorno (sección 1) están cargadas en Production (idealmente también en Preview/Development).
  • El cron /api/reminders/scan está activo en el plan y se puede ver su historial de ejecución en Vercel → Cron.
  • El dominio apunta correctamente (HTTPS válido).
  • La región configurada (iad1) responde.

9.2 Supabase

  • El proyecto está en estado saludable (sin pausa, sin alertas de storage/BD).
  • Existen las tablas: tutors, patients, medical_records, vaccinations, laboratory_exams, prescriptions, ecografias, appointments, notification_config, reminders, notification_log.
  • Existe la vista dashboard_search (con campo active).
  • Los buckets existen y están públicos: pet-photos, medical-documents, lab-exams, ecografias.
  • La función generate_numero_historia() funciona (se generan n° correlativos).
  • La migración 20260829 fue aplicada (8 tablas + patients.active + vista con active + 6 presets de config).
  • No hay errores constantes en los logs de Supabase (funciones edge / REST).

9.3 Almacenamiento (Storage)

  • Subir y ver una foto de paciente funciona (bucket pet-photos).
  • Subir y abrir un examen funciona (bucket lab-exams).
  • Subir y ver imágenes de ecografía funciona (bucket ecografias).
  • Adjuntar documento a historia funciona (bucket medical-documents).
  • Los archivos subidos tienen URL pública accesible.

10Prueba end-to-end y hoja de hallazgos

10.1 Flujo completo recomendado

  1. Entrar con el PIN → Dashboard.
  2. Crear un tutor nuevo (o usar uno de prueba).
  3. Agregar una mascota con foto → queda en Pacientes.
  4. Abrir el perfil → crear una consulta con checklist de sistemas y adjunto.
  5. Registrar una vacuna con próxima dosis a ~10 días.
  6. Subir un examen PDF/imagen → verificar analitos extraídos por IA.
  7. Agendar una cita en la agenda para dentro de una semana.
  8. Ir a Avisos → Chequear ahora → deben crearse los recordatorios de vacuna y cita (según ventanas).
  9. Probar WhatsApp (abre wa.me) y Email en un recordatorio.
  10. Marcar uno como Sin respuesta → aparece en la pestaña Seguimiento.
  11. Verificar que el dashboard muestra la cita en Próximos eventos.
  12. Verificar la vista de impresión del reporte de paciente e historia.

10.2 Verificaciones transversales

  • La app se ve y funciona en móvil (bottom nav) y desktop (sidebar).
  • El tema oscuro/claro funciona con el toggle y persiste.
  • No hay errores en la consola del navegador en las rutas principales.
  • Los tiempos de carga son razonables (sin requests colgados).
